## Context

项目已有较可靠的 legacy `Holding` 监控路径，以及由 shadow 投影填充的新 `Position` 领域。近期 change 将 Position 切换、风险工作流重做和本地扩展标记为完成并归档，但运行时仍混用权威模型：监控、价格历史和大多数前端命令使用 `Holding`；切换后的仪表盘读取 `Position`；CSV 始终写入 `Position`；多个扩展 worker 没有调度 owner。

该应用是本地、单用户、单进程工具。保护止损事实并保证受支持流程可恢复，比继续暴露未完成能力更重要。现有数据库表和 shadow 投影是未来迁移的重要资产，不能破坏。

## Goals / Non-Goals

**目标：**

- 让每个受支持的读取、写入、监控周期、告警操作和仪表盘计算一致使用 legacy 持仓权威模型。
- 防止 CLI 或 HTTP 操作产生半切换状态或不可见数据。
- 保持客户端可见 HTTP 结果和错误码稳定。
- 让质量门禁真正证明受支持 UI 流程、依赖状态、恢复边界和当前规格。
- 恢复当前主规格与未来路线图工作的真实边界。

**非目标：**

- 完成以 Position 为权威的行情监控、部分平仓、风险确认、重新布防或兼容适配器。
- 删除 Position 表、shadow 数据、归档 change 产物或迁移历史。
- 完成 Webhook 投递、CSV 可移植性、保留策略调度或浏览器系统通知。
- 替换 SQLite、迁移 runner、FastAPI、Vue 或现有视觉设计。
- 增加认证、多用户、券商连接或公网部署。

## Decisions

### 1. 通过收缩运行面实现稳定，而不是补完切换

受支持版本保持在 `legacy` 或 `shadow-read`，两者都以 `Holding` 作为唯一写入者。切换命令必须在备份、投影修改或权威状态更新前失败，并以稳定原因说明本版本不支持目标模式。

我们考虑过补完 Position 路径，但这需要第二套监控引擎、Position 行情/规则/事件更新、兼容价格和历史 DTO、前端工作流恢复以及完整迁移 E2E。这属于金融正确性影响面更大的平台补全 change，不是有界的稳定化 change。

### 2. 保留 shadow 资产，同时阻止未支持写入

可继续保留 shadow 重建、对账和只读 Position 诊断接口，用于开发与迁移分析。仅 Position 支持的写入，以及会在受支持持仓工作流之外创建 Position 事实的操作，必须返回稳定的 `409 feature_not_supported`；不需要兼容时可直接从公共路由移除。

前端不渲染已停用能力的控件。仅隐藏控件并不充分，后端守卫才是权威边界，直接 HTTP 调用也必须默认拒绝。任何环境变量都不得悄悄把这些能力提升为稳定行为。

### 3. 定义统一的受支持运行面矩阵

实现和测试使用以下显式矩阵：

| 运行面 | 稳定行为 |
|---|---|
| 持仓、仪表盘、价格、历史、监控 | legacy `Holding` 权威模型 |
| 告警 | 快照与已读操作，并导航至 Holding 详情 |
| Shadow 投影 | 只读诊断支持 |
| Position 写入与切换 | 停用 |
| CSV Position 导入导出 | 停用 |
| Webhook、保留策略 worker、浏览器系统通知 | 停用 |
| 备份恢复与隐私安全诊断 | 支持且经过验证 |

相比零散的前端功能判断，该矩阵能让 CLI、路由、文档和测试共享同一个版本边界。

### 4. 保留预期 HTTP 异常并统一运维故障契约

路由必须透传有意抛出的 `HTTPException`，并仅在边界处转换一次领域故障。全量与限定范围刷新共享同一结果到 HTTP 映射，统一处理 `refresh_busy`、`database_busy`、校验失败和未知故障。公共错误包含稳定 `error_code`；未知故障还应包含关联 ID，但不得暴露提供方响应或财务数据。

对于仍保持公共访问的 Position 和运维接口，应使用明确的 Pydantic 模型替换或约束请求字典。这样可提升校验与 OpenAPI 准确性，而无需重做应用全部响应。

### 5. 让真实浏览器 E2E 成为发布门禁

现有离线 smoke 继续作为 API/进程 smoke，并以该名称报告。浏览器测试工具使用构建后的前端和 fixture 后端，在 `390x844`、`768x1024` 与 `1440x900` 下完成创建、刷新、触发、查看告警、持仓详情和关闭流程，并断言路由可达、完成状态可见、无横向溢出、固定导航不遮挡、没有未捕获浏览器错误。

组件测试将使用确定性 API mock 挂载真实 Dashboard、Holdings、HoldingDetail、Alerts 和 Settings 视图。源码文本断言可以保留为低成本结构检查，但不能作为行为要求的验证依据。

### 6. 将主规格视为当前契约，将归档视为历史

不重写已归档 proposal 和已勾选任务清单。本 change 的 delta specs 从当前契约中移除已推迟行为，增加默认拒绝的版本要求，并在路线图中保留更完整的 Position 与扩展方向。`verify.ps1` 必须验证全部当前规格，而不仅是 active changes。

每项变更后的 requirement 至少对应一项自动化验收测试或明确的人工恢复演练。通过简短的可追溯文档或测试命名约定，让映射关系可以检查。

## Risks / Trade-offs

- [暂时移除可见功能可能让见过这些功能的用户失望] -> 将其明确记录为推迟，并保留数据结构，等待后续独立验证后重新上线。
- [数据库可能已经处于 `new-authoritative`] -> 在启动和 readiness 阶段检测并提供恢复指引；不得静默写入 legacy，也不得自动反向投影。
- [停用 CSV 导出减少一种潜在恢复路径] -> 继续支持经过验证的 SQLite 备份恢复；只有 CSV 能无损导出实际权威事实后才重新启用。
- [浏览器 E2E 增加安装时间和依赖体积] -> 使用 fixture 数据，每组视口复用一次前端构建，并将真实提供方网络测试分开。
- [主规格比路线图愿景更小] -> 这是有意选择；未来要求继续保留在路线图中，必须通过新 change 才能成为当前契约。
- [错误统一会改变响应体] -> 在现有状态码正确时继续保留，增加稳定错误码，并在发布前覆盖前端兼容性。

## Migration Plan

1. 为当前 legacy 流程、刷新错误行为、权威阶段和未完成扩展的直接调用增加表征测试。
2. 在修改前端之前，先增加默认拒绝的切换行为和后端功能守卫。
3. 修复告警导航与刷新异常处理，再移除未支持控件和孤立稳定路由。
4. 增加组件与浏览器门禁、依赖预检、隔离临时目录、完整 OpenSpec 校验和备份恢复演练。
5. 更新 README 与路线图，记录受支持运行面矩阵以及已切换数据库的恢复指引。
6. 在准备好的干净环境中连续运行两次完整验证命令，再归档 change。

回滚时恢复上一版应用代码即可，无需数据库降级，因为本 change 不删除表，也不写入新 schema。Shadow 数据仍可重建。如果应用检测到已有 `new-authoritative` 数据库，则必须按早期迁移 change 的文档恢复经过验证的切换前备份。

## Open Questions

- 无阻塞问题。重新启用 Position 权威模式、CSV 可移植性或外部投递，必须分别建立 change，并提供各自的端到端验收门禁。
