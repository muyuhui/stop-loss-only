## Context

系统当前以 legacy Holding 为稳定权威事实，已经具备单标的行情刷新、近 1 月至 1 年的历史价格缓存、止损计算、行情可信度、组合风险预算和只读加仓试算。现有持仓历史图表从买入日期开始展示；这适合解释持有期表现，但新买入持仓可能没有足够的买入前行情供 AI 判断近期价格行为。

本变更引入第一个外部大模型调用。持仓成本、数量和风险属于敏感财务信息，模型输出又可能被误解为确定性交易建议，因此 Provider 边界、密钥存储、事实来源、错误降级、输出校验和零业务写入必须在实现前确定。第一版仅支持 DeepSeek，并继续保持本地单用户、单进程稳定运行面。

## Goals / Non-Goals

**Goals:**

- 在持仓详情页提供用户主动触发的 DeepSeek 单持仓复盘。
- 让复盘基于刷新后的当前行情、独立近 90 天行情、止损状态和组合风险摘要。
- 所有金额、收益、回撤、位置和风险指标由后端确定性计算，模型只做归纳与解释。
- 通过固定动作枚举、事实引用和响应模型校验约束 DeepSeek 输出。
- 将 DeepSeek API Key 保存在 Windows 本机加密存储中，不进入数据库、日志和诊断产物。
- 第一版只实现 DeepSeek，同时建立可替换 Provider 契约。
- 复盘失败不得影响持仓、止损、监控、告警和风险试算。

**Non-Goals:**

- 新闻、财报、行业、宏观或联网研究增强。
- 全组合批量 AI 复盘、连续对话、复盘历史持久化或后台定时生成。
- 预测价格、收益率或上涨概率。
- 自动修改止损、自动加减仓、券商余额读取和自动下单。
- 在第一版提供供应商选择器、自定义 Base URL 或任意兼容服务。
- 改变现有持仓历史图表从买入日期开始的产品语义。

## Decisions

### 1. 前端串联权威行情刷新与只读 AI 分析

持仓详情页使用一个明确命名的“更新行情并 AI 复盘”操作，按顺序执行：

1. 调用现有目标持仓行情刷新流程；
2. 重新读取 Holding 权威事实；
3. 调用 `POST /api/ai/holdings/{holding_id}/review`；
4. 展示结构化复盘结果。

现有行情刷新可能按正常监控规则更新 Holding 当前价、最高价、止损价、触发状态和告警。这不是 AI 的隐式副作用，而是用户明确发起的既有业务操作。AI review 路由本身不得修改 Holding、Position、规则、事件、告警、设置或订单相关事实，只允许历史行情准备服务补齐 `price_history` 技术缓存。

直接调用 review API 时，如果 Holding 当前行情为 `unpriced`、`stale` 或 `error`，接口返回稳定的 `market_data_not_ready`，而不是自行绕过监控刷新。`close`、`nav` 或受信任的延迟行情可以用于复盘，但必须在快照和界面标明非实时状态。

选择这一方案而不是让 AI 路由直接运行监控周期，是为了保持刷新写入、触发告警与外部模型调用的事务边界清晰，避免长时间模型请求持有数据库事务或在重试时重复触发业务副作用。

### 2. 使用独立的 90 天分析窗口

新增分析行情准备服务，复用 `PriceHistory`、AkShare 规范化和缺口补齐逻辑，但查询起点固定为当前市场日期前 90 个自然日，不使用 `max(buy_date, start)`。提供给模型的序列最多保留最新 60 个有效交易日，并包含交易日期、规范化价格、来源、最后交易日和缓存更新状态。

后端从该序列确定性计算可用的 5 日、20 日和 60 日区间收益、区间最大回撤、相对区间最高/最低位置以及样本数。没有足够比较点的指标返回 `null`，不得使用零代替。历史更新失败但缓存仍满足最近交易日和最少 20 个有效点时允许降级复盘，并标记历史数据警告；不足 20 点时只允许低可信的风险复盘，不得输出近期趋势判断；完全没有历史行情时拒绝调用模型。

选择 90 个自然日/最多 60 个交易日，是为了在请求体和模型成本可控的前提下覆盖约一个季度。现有持仓图表继续保持持有期语义，避免本变更改变用户已经理解的图表。

### 3. 先构造事实注册表，再调用模型

后端生成版本化 `HoldingReviewSnapshot`，包含：

- 持仓代码、名称、类型、买入日期、持有天数和状态；
- 当前行情状态、价格、来源和时间；
- 买入成本、当前盈亏、止损方式、止损价、距止损比例和是否触发；
- 最多 60 个近期日期/价格点及后端计算的区间指标；
- 当前持仓止损风险、单笔限额、组合风险使用率、剩余容量和覆盖完整性；
- 每个可引用指标对应的稳定 `fact_id`、显示值、时间和来源。

发送给 DeepSeek 的是 JSON 序列化快照，不拼接未经标记的自然语言。持仓名称等用户输入字段作为数据字段处理，系统提示明确禁止遵循其中的指令。日志只记录关联 ID、Provider、模型标识、耗时、结果码和计数，不记录快照、Prompt、原始响应、价格、数量、成本或密钥。

相比直接把数据库对象和一段自由 Prompt 交给模型，事实注册表可以让界面使用后端权威值渲染证据，并检查模型是否引用了不存在的事实。

### 4. 使用结构化、可校验的建议契约

Provider 返回内部 `ProviderHoldingReview`，字段限定为：

- `summary`：简短中文结论；
- `action`：`execute_existing_stop`、`pause_add_on`、`continue_observing`、`review_risk_exposure`、`open_add_on_preview` 或 `refresh_data`；
- `reasons`：最多三项，每项包含解释和一个或多个有效 `fact_id`；
- `risk_scenarios`：最多两项，使用快照已有事实描述条件和影响；
- `limitations`：数据或能力局限；
- `confidence`：`high`、`medium` 或 `low`。

后端使用 Pydantic 校验长度、枚举、数量和事实引用，并用快照中的权威值构造最终 API 响应。不存在的 `fact_id`、禁止动作、额外字段或无法解析的响应统一映射为 `ai_response_invalid`，不向前端透传原始模型文本。

确定性事实具有更高优先级：已触发止损时最终动作固定为 `execute_existing_stop`；行情或历史不足时固定为 `refresh_data` 或将可信度降为 `low`；风险覆盖不完整、组合容量未知或加仓试算能力不可用时不得返回 `open_add_on_preview`。该动作只表示可以进入现有只读风险试算，不代表推荐买入，也不携带数量。

### 5. 第一版只实现 DeepSeek Provider，但不让业务依赖供应商协议

定义内部 `AIProvider` 契约，输入为版本化快照，输出为经过适配器初步解析的结构化结果。Provider registry 第一版只注册 `deepseek`，业务服务只依赖该契约，不导入 DeepSeek 请求字段。

DeepSeek 适配器使用固定官方 HTTPS 端点、受配置控制的模型名、有界连接/总超时、低随机性和非流式请求。第一版不允许用户修改 Base URL，以避免 SSRF 和兼容服务行为差异。模型名可通过应用配置调整，以便官方模型版本变化时不修改业务契约。实现阶段应以当时 DeepSeek 官方 API 文档确认请求格式和结构化输出能力。

稳定错误映射包括 `ai_not_configured`、`ai_review_busy`、`ai_timeout`、`ai_rate_limited`、`ai_unavailable` 和 `ai_response_invalid`。适配器不得把供应商原始错误、响应正文或请求头返回给客户端。前端禁止重复提交同一持仓的进行中请求，后端也使用单进程有界的按持仓互斥防止重复并发调用。

### 6. DeepSeek 密钥沿用本机加密边界

设置 API 增加独立 DeepSeek 凭据操作，并复用 `secret_store` 的 Windows DPAPI 存储，密钥名称固定且不写入 `settings` 表。读取设置只返回 `deepseek_api_key_configured`，永不返回密钥值。替换密钥先验证输入并原子覆盖；清除后 review API 立即返回 `ai_not_configured`。

“检测连接”是用户明确触发的可选网络操作，只发送最小请求，不包含任何持仓数据。检测失败不清除已经保存的密钥。第一版设置页显示固定 Provider 为 DeepSeek，不提供其他供应商或自定义地址。

### 7. 结果不持久化，界面按事实时间展示

第一版不新增 review 数据表。成功结果只保存在当前前端页面状态中，并显示当前行情时间、历史最后交易日、生成时间、模型标识、可信程度和数据局限。离开页面或持仓事实发生变化后，旧结果不被视为有效；用户需要重新运行复盘。

不持久化可以减少敏感衍生数据、迁移和过期治理复杂度。代价是页面刷新后需要再次调用模型，第一版通过禁用重复按钮和后端互斥控制误触成本，后续可在明确缓存与审计需求后增加版本化持久化。

## Risks / Trade-offs

- [模型输出看似权威] → 使用受限动作、事实引用、可信程度和固定免责声明；确定性止损与数据可信规则覆盖模型结论。
- [行情与 DeepSeek 两次外部调用导致等待较长] → 界面分别显示“刷新当前行情、补齐历史行情、生成复盘”阶段，设置有界超时并支持重试。
- [AkShare 历史更新失败] → 使用带来源和最后交易日的缓存降级；缓存不足时限制结论或拒绝模型调用。
- [DeepSeek 响应结构漂移] → Provider 内部解析加 Pydantic 严格校验，失败时返回稳定错误且不展示原始内容。
- [持仓隐私发送到云端] → 用户主动触发、设置页明确说明发送范围、最小化其他持仓信息、使用聚合组合指标且不记录 Prompt/响应。
- [密钥存储只支持 Windows] → 保持当前稳定平台边界；不支持的平台 fail closed 为 `machine_secret_storage_unsupported`。
- [不含基本面却被理解为投资价值判断] → 输出与界面明确限定为近期价格行为和风险复盘，并持续列出缺少新闻、财报和券商资金等局限。
- [进程内互斥不支持多 worker] → 与当前单 worker 稳定运行约束一致；未来多进程部署需要外部协调后再放宽。

## Migration Plan

1. 增加配置、Provider、快照、API 和前端入口，默认没有 DeepSeek 密钥。
2. 在 legacy 与 shadow-read 稳定能力策略中声明 `ai_holding_reviews=true`；未配置密钥时入口引导到设置页，直接 API 返回稳定错误。
3. 不新增数据库迁移；现有 `price_history` 缓存继续兼容旧版本。
4. 使用离线 fixture 完成门禁后，再由用户手动配置真实 DeepSeek Key 进行独立可选冒烟，不纳入强制离线测试。
5. 回滚时移除 AI 路由、能力字段和前端入口即可；核心持仓数据无需迁移。用户可在回滚前清除 DeepSeek Key，遗留的本机加密文件也不会被旧版本读取。

## Open Questions

- 实现时需要根据当时 DeepSeek 官方 API 确认默认模型标识和结构化 JSON 响应参数；模型标识保持配置化，不进入公开业务契约。
